# Repository Guidelines

## Project Structure & Module Organization

Library source lives in `src/`, grouped by utility category such as `array/`,
`object/`, and `string/`. Each category exposes a local `index.ts`, while
`src/index.ts` defines the package's public API. Category-level Vitest suites
live in `tests/*.test.ts`; type-contract tests use names such as
`tests/types.api.test.ts`. The VitePress site is under `docs/`, with API pages
in `docs/api/`. `dist/` is generated by tsdown and must not be edited manually.

## Build, Test, and Development Commands

- `pnpm install` installs the workspace with the pinned pnpm version.
- `pnpm dev` rebuilds the library in watch mode.
- `pnpm build` creates ESM output and declarations in `dist/`.
- `pnpm test` runs the Vitest suite once.
- `pnpm typecheck` validates strict TypeScript types without emitting files.
- `pnpm lint` and `pnpm format:check` run Oxlint and verify Oxfmt output.
- `pnpm run release:check` runs formatting, linting, type checks, and tests.
- `pnpm docs:dev` serves the documentation locally; `pnpm docs:build` verifies
  its production build.

Use Node `^22.13.0 || >=24`, as declared in `package.json`.

## Coding Style & Naming Conventions

Follow `.editorconfig` and Oxfmt: two-space indentation, LF endings, single
quotes, trailing commas, and no semicolons. Keep utilities small, side-effect
free, and tree-shakable. Use camelCase for functions and files
(`filterFalsy.ts`), PascalCase for exported types, and descriptive option types
such as `ObjectOmitOptions`. Export a new public utility from both its category
barrel and `src/index.ts`. Add JSDoc examples for public APIs when behavior is
not obvious.

## Testing Guidelines

Place tests in the matching category suite and use Vitest's `describe`, `it`,
and `expect`. Cover normal behavior, boundary values, invalid inputs, and type
inference where applicable; inline snapshots are appropriate for structured
results. No numeric coverage threshold is configured, so every behavior change
should include focused regression tests. Run `pnpm test` and `pnpm typecheck`
before submitting.

## Commit & Pull Request Guidelines

History follows Conventional Commit-style subjects: `feat(array): add groupBy`,
`fix(dom): missing export ...`, `docs: ...`, and `chore: ...`. Use an imperative,
concise subject; add `!` for breaking changes. Pull requests should explain the
motivation and behavior change, link relevant issues, and list validation run.
Update matching `docs/api/` pages for public API changes and include screenshots
only when documentation presentation changes.
